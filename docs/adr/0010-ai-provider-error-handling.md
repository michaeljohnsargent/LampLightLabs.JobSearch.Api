# ADR 0010: AI Provider Error Handling

## AI provider failures are translated, not propagated

All three AI endpoints (`/api/rag/match`, `/api/v2/ai/chat`, `/api/v2/sk/chat`) call `ClaudeChatService` and/or `ResumeVectorStoreService`/`SemanticKernelChatService`, which wrap the Anthropic and OpenAI .NET SDKs respectively. Both SDKs throw exceptions whose messages can contain account IDs, exact usage/quota figures, or billing-page URLs on quota/billing failures - real information disclosure if returned to an anonymous client, on top of the usual stack-trace reconnaissance risk. `AiProviderException` (`Provider` + `Reason`: Billing/Unauthorized/RateLimited/Unavailable/Unknown) is the one shape every controller catches; `OpenAiExceptionTranslator` is the shared translation for the two OpenAI-backed call sites (embeddings and Semantic Kernel chat) so that logic isn't duplicated. Controllers log the full original exception via `ILogger<T>` (job description hashed with SHA-256 rather than logged raw) and return only a generic message - `429` for `RateLimited`, `503` for everything else - plus a catch-all `catch (Exception ex)` so even an unrelated failure (e.g. malformed LLM JSON) can't leak raw detail either.

## Anthropic billing-error detection matches on `ErrorType`, not HTTP status

`ClaudeChatService`'s original heuristic keyed the `Billing` reason off `AnthropicForbiddenException` (HTTP 403). Per Anthropic's own API error documentation, insufficient credit balance actually comes back as HTTP 400 with `error.type: "billing_error"` - so the 403-based check could never fire for the scenario it existed to catch. The Anthropic .NET SDK parses `error.type` out of the response body for every `AnthropicApiException` subtype regardless of status code and exposes it as the `ErrorType` property (`AnthropicExceptionFactory.ExtractErrorType`), so the fix matches on `ex.ErrorType == ErrorType.BillingError` instead - this catches the real failure on whatever status code Anthropic pairs it with, and won't misreport an unrelated 400 (e.g. a malformed request, `error.type: "invalid_request_error"`) as a billing issue. `ClaudeChatServiceTests` pins this against the real SDK exception-translation path (a fake `HttpMessageHandler` returns canned Anthropic error bodies, exercised through the actual `AnthropicClient`) rather than re-describing the expected behavior, since the original bug shipped silently in an untested code path.
